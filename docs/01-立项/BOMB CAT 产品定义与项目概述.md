## 1. 项目背景

### 1.1 为什么做 BOMB CAT

已确认的产品方向是：BOMB CAT 是一款原创多人在线派对卡牌游戏，玩法流程、交互体验与产品功能可以参考《Exploding Kittens 2》，但品牌、Logo、卡面、插画、角色、美术素材、动画、音效与文案必须原创。

以下动机属于产品规划假设，仓库内没有市场调研、用户访谈或竞品数据支撑，不能作为已验证的市场结论使用：

1. 卡牌派对游戏的单局时间短、规则易讲解，适合在朋友聚会、线上语音、碎片时间等场景传播。
2. 网页端无需下载安装，通过分享链接或房间号即可加入，降低了熟人开局的传播成本。
3. 爆炸猫类玩法具备「高风险抽牌 + 互相陷害」的强情绪点，天然适合产生可分享的对局片段与社交话题。
4. 现有同类产品以移动应用为主，网页端即开即玩的产品形态存在体验差异空间。

上述判断需要在立项评审时被质疑和验证，不能写进对外宣传材料。

### 1.2 产品要解决的问题

以下为产品假设层面的问题拆解，用于推导产品方向，未经用户调研验证。

| 问题 | 具体表现 | 产品应对方向 |
| --- | --- | --- |
| 熟人开局门槛高 | 需要下载、注册、加好友、建房间，链路过长导致「想玩一局」的冲动被消耗 | 游客身份 + 分享链接/房间号直达牌局 |
| 规则讲解成本高 | 派对现场需要有人负责讲规则，新手容易在关键节点操作错误 | 规则内聚在交互中，关键节点给出明确提示与二次确认 |
| 线上对局公平性存疑 | 客户端可被篡改，手牌等秘密信息可能泄露 | 服务端权威判定，客户端只负责表现与输入 |
| 单机与联机体验割裂 | 单机 AI 与真人局使用两套逻辑，行为不一致 | AI 与真人共用同一套规则引擎，AI 只是另一种行动者 |
| 同类产品美术同质化 | 直接模仿会带来知识产权风险，也难以形成品牌记忆 | 从立项阶段就建立原创美术与品牌规范 |

### 1.3 为什么选择在线派对卡牌方向

现有支撑条件（第 1、3 条为资料事实，第 2 条为技术判断）：

1. 核心玩法已有可执行的规则参考 `GAME_RULES_SPEC.md` v1.1，包含牌组构成、状态机、卡牌效果、组合牌、抽空处理、胜负判定与 18 条验收用例，具备工程化基础。
2. 玩法本身对实时性要求低于动作类游戏，回合制允许一定的网络延迟，技术风险相对可控。
3. 产品形态确定为官网、游戏网页端、管理后台三部分，网页端移动优先，适合派对场景下的临时组局。

需要说明的边界：以上是「可行性判断」，不代表市场已被验证。首发地区、目标用户规模、获客方式均未确认。

## 2. 产品定位

### 2.1 一句话定位

已确认：BOMB CAT 是一款面向朋友聚会与线上社交场景、以网页为载体的原创多人在线派对卡牌游戏，玩家通过游客身份即可开局。完整产品规划支持 AI 对战、好友房间与公开匹配三种模式；公开匹配的首期上线时间尚未确定（见 8.4）。

### 2.2 产品是什么，不是什么

| 是 | 不是 |
| --- | --- |
| 原创美术与品牌的派对卡牌游戏 | 《Exploding Kittens 2》的换皮复刻或素材搬运 |
| 以网页端为核心入口的跨端产品 | 需要下载安装的原生手游或客户端游戏 |
| 服务端权威判定的在线多人游戏 | 客户端自行结算、可被本地篡改的联机游戏 |
| 一局约 5–15 分钟（参考规则文件的单局时长，属于待验证的设计目标） | 长周期养成、重度策略或实时动作类游戏 |
| 支持游客即开即玩的低门槛产品 | 强制注册、强制手机号或实名后才能体验的产品（合规要求另行确认） |
| 包含官网、游戏端、管理后台的完整产品 | 只有单页游戏的 Demo 或一次性原型 |
| 首期聚焦稳定公平的在线对局 | 首期即包含完整商业化、赛季、赛事的产品 |

### 2.3 核心产品价值

1. 低门槛开局：从打开链接到进入牌局，尽量减少注册、下载、加好友等前置步骤。
2. 公平可信：所有影响胜负的判定在服务端完成，玩家手牌等秘密信息不下发给无关客户端。
3. 情绪密度高：抽牌、陷害、拆弹、反制等节点集中产生紧张与笑点，适合派对传播。
4. 规则一致：AI 与真人、单机与联机使用同一套规则引擎，避免同一张卡在不同模式下行为不同。
5. 品牌可延展：原创角色与视觉体系可支撑后续装扮、成长与内容更新。

### 2.4 主要体验特点

| 特点 | 具体含义 | 对设计的约束 |
| --- | --- | --- |
| 即开即玩 | 游客身份进入，分享链接或房间号即可加入 | 首屏不能出现强制注册墙；身份失效要有恢复路径 |
| 回合清晰 | 任何时刻玩家都能判断「轮到谁、我还要行动几次」 | 牌桌必须常显当前玩家与剩余回合 |
| 操作可逆 | 出牌前可取消，关键操作有确认 | 需要明确的选牌态、取消态与二次确认 |
| 信息分层 | 公开信息全量展示，秘密信息只对本人可见 | 手牌、先知结果、拆弹位置必须服务端裁剪 |
| 失败可解释 | 被淘汰、被反制、被攻击时能看懂原因 | 关键事件需要有可回看的提示，而不是只播动画 |
| 异常可恢复 | 断线、刷新、切后台后能回到对局 | 需要身份凭证、对局快照与重连机制 |

### 2.5 差异化方向

以下为产品假设，需评审确认：

1. 网页优先：以链接分享为核心的传播方式，区别于必须安装客户端的同类产品。
2. 原创角色叙事：用自有角色与世界观承载卡牌与装扮，而不是套用现成猫咪形象。
3. 规则透明：把规则说明、判定依据做成产品内可查的能力，降低「为什么我被淘汰」的争议。
4. 三端一体：官网承担介绍与入口，游戏端承担对局，后台承担运营，三者共享同一身份与数据口径。
5. 公平优先：首期不以商业化和付费深度为目标，先把公平与稳定做扎实。

### 2.6 与竞品的关系边界

已确认：可以参考玩法流程、交互体验与产品功能，不复制品牌、Logo、卡面设计、插画、角色、美术素材、动画、音效与文案。

执行口径：

- 可以研究「玩家在某个环节需要完成什么」。
- 不可以复制「竞品用什么图形、什么文案、什么布局、什么角色」。
- 调研记录中的截图只用于内部分析，不进入设计交付物。
- 具体调研任务见 `docs/02-竞品调研/01-调研总览与任务清单.md`，本文不展开竞品结论。

## 3. 目标用户

说明：本节是初步用户假设，不代表已完成用户调研，也没有用户规模、年龄分布、付费意愿等数据支撑。用户分层用于指导首期设计与评审讨论，不作为对外结论。

### 3.1 用户分层

| 用户类型 | 典型画像（假设） | 主要需求 | 典型场景 | 体验诉求 | 对产品的含义 |
| --- | --- | --- | --- | --- | --- |
| 休闲游戏玩家 | 每周玩几次轻量游戏，不愿学习复杂规则，习惯在手机浏览器或应用内即点即玩 | 快速开始、规则易懂、单局不拖沓、失败不挫败 | 通勤、午休、睡前碎片时间 | 希望 30 秒左右理解怎么玩（产品假设，待验证）；不需要读长说明；随时可以退出 | 首屏必须有直接开局入口；新手引导要内嵌在对局中；AI 模式承担教学与练习职责 |
| 好友聚会及社交玩家 | 2–5 人线下同处或线上语音，边聊边玩，重视互动与情绪 | 快速组局、邀请方便、过程有笑点、能互相影响 | 宿舍、聚餐、团建、语音房 | 分享链接即可加入；等待时间短；能看见别人做了什么；有互动表达方式 | 房间号与分享链接是核心入口；等待大厅要能显示人数与准备状态；互动能力是否首期实现待确认（8.4），结构上应预留 |
| 喜欢策略和卡牌玩法的玩家 | 熟悉卡牌游戏，关注规则严谨、信息透明度与胜负合理性 | 规则自洽、判定公平、有决策空间、能复盘关键节点 | 自主匹配、连续多局 | 规则无歧义；随机与判定可信；能看到关键事件；有成长与统计 | 服务端权威与规则一致性是硬要求；结算需要提供关键数据；排行榜与成长属于后续承接 |

### 3.2 用户假设的共同点

1. 三类用户都要求「开始一局」的路径短，区别只在于开局后的深度。
2. 三类用户都依赖手机浏览器，桌面端是兼容而非主战场。
3. 三类用户对「不公平」的容忍度都很低，尤其怀疑客户端可以看牌或改结果时，会直接流失。
4. 社交玩家对等待与断线的容忍度最低，因为等待会打断现场气氛。

### 3.3 初步优先级（假设）

| 优先级 | 用户群 | 理由 |
| --- | --- | --- |
| 首要 | 好友聚会及社交玩家 | 与「分享链接即开即玩」的产品形态最匹配，也是派对卡牌的核心场景 |
| 次要 | 休闲游戏玩家 | 通过 AI 对战承接，是留存与转化的基础 |
| 兼顾 | 策略卡牌玩家 | 不是首期设计重心，但规则严谨性必须满足其底线要求 |

### 3.4 非目标用户

- 追求长线数值养成与重度社交体系的玩家（首期不提供）。
- 期待单机剧情、关卡闯关或 PVE 战役的玩家（产品不含此类内容）。
- 需要竞技赛事、观战、战队体系的玩家（暂不纳入规划）。
- 无法使用现代浏览器的设备用户（具体兼容范围待确认）。

## 4. 产品形态与端侧规划

### 4.1 三端总体关系

```
                    ┌──────────────────────────────┐
                    │           官网                │
                    │  介绍 / 入口 / 帮助 / 公告     │
                    └──────────────┬───────────────┘
                                   │ 引导进入
                                   ▼
┌──────────────────────────────────────────────────────────┐
│                      游戏网页端                            │
│  身份建立 → 游戏大厅 → 三种模式 → 核心牌局 → 结算           │
│  移动端优先，兼容 PC 与 PWA                                 │
└──────────────┬───────────────────────────┬───────────────┘
               │ 业务数据（只读/受控）        │ 对局与房间数据
               ▼                           ▼
        ┌──────────────────────────────────────────┐
        │               管理后台                     │
        │  玩家 / 房间 / 对局 / 基础运营 / 数据查看     │
        └──────────────────────────────────────────┘
```

说明：上图表达的是职责关系，不代表技术调用方向。具体接口、部署与数据流属于技术设计阶段内容。

### 4.2 官网

| 项 | 内容 |
| --- | --- |
| 目标用户 | 未接触过产品的新玩家、通过分享或搜索来到官网的访客、回流玩家、合作方 |
| 核心职责 | 说明产品是什么、怎么玩、如何进入游戏；承载品牌形象与基础帮助 |
| 主要功能范围 | 产品介绍与玩法说明、游戏入口、常见问题与帮助、公告与更新说明、隐私与用户协议入口 |
| 与其他端关系 | 不承载对局；通过入口跳转游戏网页端；公告与帮助内容与游戏内说明保持同一口径 |
| 首期范围 | 仅最小入口与基础说明：讲清产品、进入游戏、查看基础帮助、隐私协议入口、展示后台发布的基础公告 |
| 首期不做 | 不做社区论坛、不做内容社区、不做公告编排工具、不做多语言；是否提供账号中心待确认（Q11、Q20）。公告运营与账号入口等增强能力见 8.4 |

### 4.3 游戏网页端

| 项 | 内容 |
| --- | --- |
| 目标用户 | 实际参与对局的玩家 |
| 核心职责 | 承载身份、大厅、各模式、完整对局与结算，是产品的核心使用场所 |
| 主要功能范围 | 游客身份建立与恢复、游戏大厅、AI 对战、好友房间、公开匹配（是否首期上线待定）、核心牌桌、游戏内提示、结算页、设置与帮助 |
| 终端要求 | 移动端优先，竖屏体验为主；兼容 PC 浏览器；支持 PWA 安装（具体能力范围待确认） |
| 与其他端关系 | 从官网进入；对局与房间数据由服务端判定；后台可查看与运营，但不能绕过规则改变胜负（后台干预能力待确认 Q19） |
| 首期范围 | 跑通一局完整、稳定、公平的对局（含 AI 单人对战与好友在线对战），包含必要的异常恢复 |
| 明确不做 | 不在客户端做胜负判定；在线对局不在客户端保存唯一状态 |

### 4.4 管理后台

| 项 | 内容 |
| --- | --- |
| 目标用户 | 运营人员、客服、管理员（角色划分待确认） |
| 核心职责 | 基础运营、玩家管理、游戏房间管理、数据管理，支撑线上问题排查 |
| 主要功能范围 | 玩家查询与状态查看、房间与对局查询、基础运营配置（公告等）、异常与投诉处理、数据统计与看板（后续） |
| 与其他端关系 | 读取游戏端产生的数据；是否具备强制结束对局、封禁、补发等干预能力待确认（Q19） |
| 首期范围 | 仅运营与故障排查所需的最小能力：查询玩家、查询房间与对局、发布基础公告（展示于游戏端与官网） |
| 首期不做 | 不做数据看板与报表、不做批量运营工具、不做财务结算系统、不做数据仓库；复杂权限矩阵与对局干预能力待确认（Q19）。数据统计与干预工具等增强能力见 8.4 |

### 4.5 端间共享能力

| 能力 | 说明 | 涉及端 |
| --- | --- | --- |
| 身份 | 游客凭证的签发与恢复，后续可能扩展账号绑定 | 官网、游戏端、后台 |
| 规则口径 | 玩法说明、帮助文案、卡牌描述必须同源 | 官网、游戏端 |
| 数据口径 | 玩家、房间、对局、结算数据的定义一致 | 游戏端、后台 |
| 公告 | 后台发布，官网与游戏端展示 | 三端 |
| 版本 | 三端版本与规则版本需要可对应，便于排查 | 三端 |

### 4.6 端侧边界原则

1. 游戏端是唯一的对局场所，官网与后台都不产生对局状态。
2. 任何影响胜负的判断只在服务端发生。
3. 后台的运营动作不得静默修改历史对局结果；如需干预，必须可审计（是否具备该能力待确认）。
4. 三端共用一套身份与规则口径，不允许出现同一规则在不同端描述不一致。
5. 官网与管理后台的首期存在不代表首期要做完整版本；首期只保留游戏运行与基础运营所需的最小能力，增强能力见 8.4。

## 5. 核心游戏模式

### 5.1 模式总览

| 模式 | 一句话说明 | 使用场景 | 是否首期 | 与其他模式的关系 |
| --- | --- | --- | --- | --- |
| AI 单人对战 | 玩家与 AI 行动者完成一局（AI 数量待确认） | 练习规则、等待好友、碎片时间 | 是 | 承担教学与练习职责；不计入公开竞技排行榜 |
| 好友在线对战 | 通过分享链接或房间号，与熟人在同一房间开局 | 聚会、语音房、宿舍、团建 | 是 | 派对场景的核心模式；不依赖好友关系链 |
| 公开玩家匹配 | 由系统把互不相识的玩家组成一局 | 独自在线、想立刻开局 | 首期候选（Q13） | 属于完整产品规划；首期不上线不代表取消该模式；是否允许 AI 补位待确认 Q08 |

AI 与服务端权威的边界（产品约束，技术实现方式在技术设计阶段确定）：

1. 服务端掌握完整权威牌局状态，包括 AI 与其他玩家的隐藏信息（手牌、先知结果、拆弹插入位置）。
2. 真人客户端只能获得当前真人玩家有权访问的信息，不得获得 AI 或其他玩家的隐藏信息。
3. 不得为了在客户端运行 AI，而把 AI 的私有手牌或其他隐藏信息下发给真人客户端。
4. AI 与真人共用同一套规则引擎，AI 只是另一种行动者；AI 的每次行动都必须经过与真人相同的统一规则校验。
5. 最终牌局状态由服务端判定与更新，客户端不能自行决定胜负、淘汰或抽牌结果。
6. AI 决策的具体执行位置属于技术设计事项，但必须满足以上第 1 至 5 条；该选择的约束见 Q22。
7. 首期 AI 对战不纳入公开竞技排行榜；排行榜与成长整体后置，是否调整见 Q18。

### 5.2 AI 单人对战

基本场景：玩家想先熟悉规则，或暂时没有真人对手，选择 AI 模式直接开始。

核心流程：

```
大厅选择 AI 对战
  → 选择难度（首期提供哪些档位待确认 Q15）
  → 创建对局并分配 AI 行动者（AI 决策执行位置由技术设计决定，不得突破 5.1 的边界）
  → 玩家与 AI 按同一规则引擎轮流行动
  → 对局结束 → 结算 → 再来一局或返回大厅
```

已确认约束与安全边界：

- AI 与真人共用规则引擎。
- 首期 AI 对战不计入公开竞技排行榜。
- AI 的决策逻辑与难度分级属于策划与算法设计内容，本文不定义具体策略。
- AI 决策无论在哪执行，都不得使真人客户端获得 AI 的隐藏信息；服务端始终掌握完整权威状态（见 5.1）。

本文不预设的内容：AI 人数、难度档位、AI 局是否计入成长与任务、AI 局是否可暂停、AI 局是否保存历史对局。这些均在待确认清单中。

### 5.3 好友在线对战

基本场景：一名玩家创建房间，把链接或房间号发给朋友，朋友进入房间，人数满足后开始。

核心流程：

```
玩家 A 在大厅选择好友对战
  → 创建房间，得到房间号与分享链接
  → A 把链接或房间号发给朋友
  → 玩家 B/C/D 通过链接直达或输入房间号加入
  → 房间内显示座位、人数与准备状态
  → 满足开局条件后由房主开始（房主权限待确认 Q21）
  → 进入对局 → 结算 → 返回房间再来一局或返回大厅
```

已确认的约束与首期范围：

- 好友可以通过分享链接或房间号加入。
- 首期不要求建立好友关系即可开局；邀请分享与好友关系链的边界见 7.4。
- 房间与对局由服务端管理。

本文不预设的内容：房间人数上下限、是否需要全员准备、房主能否踢人、掉线后房间如何处理、是否允许观战、是否允许自定义规则。以上均需产品决策，见第 11 节。

### 5.4 公开玩家匹配

基本场景：玩家独自在线，希望系统直接为自己组一局。

核心流程：

```
玩家在大厅选择公开匹配
  → 进入匹配队列，界面显示匹配状态（可见信息待确认）
  → 服务端凑齐满足条件的一局
  → 匹配成功，进入对局准备或直接开局（具体形态待确认）
  → 对局 → 结算 → 再来一局 / 返回匹配 / 返回大厅
```

已确认的约束：

- 属于产品三种核心模式之一。
- 对局由服务端权威判定。

本文不预设的内容：匹配人数、是否允许 AI 补位、匹配超时后的处理、是否允许取消、是否按段位或地区匹配、匹配中能否切换模式。公开匹配属于完整产品规划的核心模式；首期是否上线需结合在线人数与运营节奏判断（Q13）。首期不上线只表示排期后移，不表示永久取消该模式。

### 5.5 模式设计注意点

1. 三种模式的牌桌与卡牌交互应当一致，差异只体现在「对手是谁、如何开始、如何结算」，避免维护三套界面。
2. AI 模式是新手理解规则的主要途径，其提示强度可以高于真人模式，但规则判定不能放宽。
3. 好友模式要优先保证「分享即加入」的成功率，链接失效、房间满员、对局已开始都需要明确提示。
4. 匹配模式要处理「人不够」的现实问题，但补位策略会改变对局性质，不能由开发自行决定。

## 6. 核心游戏体验

### 6.1 完整体验路径

```
进入游戏 → 身份建立 → 选择模式 → 创建或加入游戏 → 游戏准备
   → 正式对局 → 游戏结束 → 结算 → 再次游戏
```

### 6.2 分阶段说明

| 阶段 | 玩家目标 | 系统需要完成的事 | 玩家可感知的反馈 | 异常与待确认点 |
| --- | --- | --- | --- | --- |
| 1 进入游戏 | 打开产品，确认这是什么 | 加载游戏端；判断是否已有可用身份；判断是否有可恢复的对局 | 首屏加载态、产品标识、进入大厅的入口 | 加载失败、浏览器不兼容、从失效链接进入时的提示 |
| 2 身份建立 | 无需注册就开始玩 | 签发或恢复游客身份凭证；建立最小玩家档案 | 无需填写表单即可进入大厅；显示游客标识 | 凭证丢失、换设备、清缓存后的恢复方式（Q10） |
| 3 选择模式 | 决定怎么玩 | 展示当前可用模式入口与必要说明 | 各入口的差异说明、当前在线情况（可见范围待确认） | AI 局与联机局的能力差异要让玩家可预期 |
| 4 创建或加入游戏 | 真正进入一局 | AI 局：创建对局；好友局：创建房间或校验房间号；若当前版本提供匹配：进入队列 | 房间号、分享入口、匹配中状态、加入成功或失败原因 | 房间不存在、已满、已开局、链接过期、匹配超时（Q09、Q21） |
| 5 游戏准备 | 确认可以开始 | 校验人数与开局条件；分配座位与先后手；初始化牌局 | 座位、人数、准备状态、开局倒计时（是否倒计时待确认） | 人数不足、玩家退出、房主离开、准备状态不同步 |
| 6 正式对局 | 完成一局游戏 | 服务端维护牌局状态；按规则推送可见状态；处理行动与响应 | 当前回合、剩余回合、手牌、牌库张数、弃牌堆、关键事件提示 | 断线、超时、刷新、切后台、并发操作、动画与状态不同步（Q05–Q07） |
| 7 游戏结束 | 知道谁赢了、为什么 | 按规则判定终局；固化结果；生成结算数据 | 胜负结果、最后关键事件 | 极端终局（如牌库抽空）需要有明确解释口径 |
| 8 结算 | 看到本局表现 | 展示胜负、关键数据；按确认的范围发放奖励 | 结算页、数据项、返回入口 | 奖励范围未确认；AI 局是否计入统计未确认 |
| 9 再次游戏 | 继续玩或离开 | 支持再来一局、返回房间、返回大厅 | 一键再来、房间保持状态 | 对手已离开、房间已解散、匹配是否需要重新排队 |

### 6.3 体验设计要点

1. 第 2 步是产品门槛的关键：不能出现强制注册、强制授权、强制填资料。
2. 第 4 步是流失高发点：分享链接与房间号的失败原因必须具体，不能只提示「加入失败」。
3. 第 6 步是体验主体：玩家在任何时刻都应能回答「现在轮到谁、我能不能操作、我刚才发生了什么」。
4. 第 7 至 8 步是情绪收尾：胜负要可解释，尤其是被反制、被攻击、抽到爆炸猫导致的失败。
5. 第 9 步决定连续对局率：减少从结算回到牌局的步骤。

## 7. 产品功能全景

### 7.1 模块地图

```
基础层        玩家身份
              │
入口层        游戏大厅 ── 官网
              │
玩法层        AI 对战 │ 邀请与好友 │ 房间系统 │ 玩家匹配
              └────────┬─────────┘
                       ▼
核心层                 核心牌局
                       │
              ┌────────┴────────┐
              ▼                 ▼
反馈层      游戏内互动        游戏结算
              │                 │
长线层      玩家成长 ──────── 装扮系统
              │
支撑层        管理后台
```

说明：图中位置表达职责分层，不代表开发顺序。首期实际范围见第 8 节。

### 7.2 模块职责

| 模块 | 定位 | 核心职责 | 与其他模块的关系 | 首期 |
| --- | --- | --- | --- | --- |
| 玩家身份 | 基础层 | 游客凭证签发与恢复、玩家最小档案、身份状态管理 | 所有模块的前置依赖 | 是 |
| 游戏大厅 | 入口层 | 聚合模式入口、身份信息、公告与帮助入口 | 连接身份与各模式入口 | 是 |
| AI 对战 | 玩法层 | 创建 AI 局、驱动 AI 行动者、承接新手练习 | 复用核心牌局规则引擎 | 是 |
| 邀请与好友 | 玩法层 | 邀请分享（链接、房间号）属于首期；好友添加、好友列表与关系管理属于后续 | 为房间系统提供邀请入口 | 邀请分享：是；好友关系链：否 |
| 房间系统 | 玩法层 | 创建房间、房间号、座位、准备状态、开局条件 | 承载好友对战 | 是 |
| 玩家匹配 | 玩法层 | 匹配队列、凑局、匹配结果通知 | 复用房间与牌局能力 | 首期候选（Q13） |
| 核心牌局 | 核心层 | 服务端权威的牌局状态、回合推进、出牌与响应、抽牌与终局判定 | 被当前可用模式复用 | 是 |
| 游戏内互动 | 反馈层 | 表情、快捷语、系统提示等表达方式 | 依附于牌局 | 首期候选（待确认） |
| 游戏结算 | 反馈层 | 胜负展示、关键数据、奖励发放、再来一局 | 依赖牌局结果 | 是（奖励范围待确认） |
| 玩家成长 | 长线层 | 等级、任务、成就、排行榜等长线目标 | 消费对局结果 | 后续 |
| 装扮系统 | 长线层 | 角色外观、装扮获取与装备、展示位 | 依赖身份与成长 | 后续 |
| 管理后台 | 支撑层 | 玩家、房间、对局查询与基础运营 | 读取游戏端数据 | 是（最小） |
| 官网 | 支撑层 | 产品介绍、游戏入口、帮助与公告 | 为游戏端导流 | 是（最小） |

### 7.3 模块关系说明

1. 身份是所有能力的前提：没有可恢复的身份，游客模式下的对局记录、成长与装扮都无处归属。
2. 核心牌局是唯一不可替代的模块，其余模块围绕它提供入口、对手、反馈与长线目标。
3. 首期不建设好友关系链，只保留邀请与分享能力；两者的边界见 7.4，避免把社交体系建设成本前置。
4. 房间系统是好友对战与公开匹配的公共载体；若匹配进入首期，两者应尽量复用同一套房间与座位模型。
5. 成长与装扮必须建立在稳定的对局数据之上，因此排在首期之后。
6. 后台与官网是支撑端，不能反向依赖游戏端未稳定的内部结构。

### 7.4 邀请分享与好友关系链的边界

首期所说的「好友对战」是指熟人通过链接或房间号进入同一房间，并不要求双方在系统内已经成为好友。两者必须区分，避免开发把首期理解为建设完整好友系统。

| 能力 | 首期 | 后续版本 | 说明 |
| --- | --- | --- | --- |
| 创建房间并生成分享链接 | 是 | 保留 | 好友对战的基础能力 |
| 通过房间号加入 | 是 | 保留 | 不需要好友关系 |
| 邀请状态提示（已邀请/已加入） | 是 | 保留 | 只服务于当前房间，不形成长期关系 |
| 添加好友与好友申请 | 否 | 待规划 | 是否需要、何时纳入由产品规划决定 |
| 好友列表与在线状态 | 否 | 待规划 | 依赖身份体系与社交运营方案 |
| 好友关系管理（备注、删除、拉黑） | 否 | 待规划 | 与举报、屏蔽等安全能力一并考虑 |
| 邀请历史与再邀请 | 否 | 待规划 | 依赖好友关系链或历史对局 |

开发含义：

1. 首期不需要好友关系数据模型，也不需要有好友申请、同意、删除等流程。
2. 首期邀请只与「房间」绑定，房间结束或解散后邀请关系不保留。
3. 后续若引入好友关系链，应能复用现有身份与房间能力，不推翻首期结构。

## 8. 产品范围与首期目标

### 8.1 范围分层

| 层次 | 定义 | 判断标准 |
| --- | --- | --- |
| 完整产品规划 | 产品最终计划具备的能力 | 写入产品定位与功能全景，不代表首期交付 |
| 首期必须交付 | 缺少即无法成立首期产品 | 没有它无法完成一局公平、稳定的在线对局，或无法支撑基础运营 |
| 首期候选能力 | 有价值，但依赖成本与运营条件 | 不影响核心闭环成立，需在立项评审逐项决定 |
| 后续版本能力 | 不阻塞首期上线 | 依赖首期数据、原创资产或用户规模 |

本分层用于回答三个问题：产品最终要做什么、首期缺少哪些能力就不成立、哪些能力可以推迟。各层包含的具体能力仍需产品经理评审确认。

### 8.2 完整产品规划

已确认：完整规划包含玩法、多人、AI、社交、成长等能力（任务书第三节第 6 条）。对应第 7 章模块，完整规划包含：

| 能力域 | 包含模块 | 说明 |
| --- | --- | --- |
| 身份与入口 | 玩家身份、游戏大厅、官网 | 游客身份是基础；官网承担介绍、入口与帮助 |
| 对局模式 | AI 单人对战、好友在线对战、公开玩家匹配 | 三种模式均属于完整规划，不等同于首期范围 |
| 对局核心 | 房间系统、核心牌局、游戏结算 | 当前可用模式共用 |
| 社交与表达 | 邀请分享、好友关系链、游戏内互动 | 分阶段建设；首期至少包含邀请分享，游戏内互动是否进入首期见 8.4 |
| 长线成长 | 玩家成长、排行榜、装扮系统 | 依赖对局数据与原创资产 |
| 运营支撑 | 管理后台 | 承担基础运营、玩家、房间与数据管理 |

商业化（内购、广告、会员）是否纳入完整规划仍待决策（Q25），本文不将其列为既定规划内容。

### 8.3 首期必须交付

已确认：首期优先跑通一局完整、稳定、公平的在线多人游戏；首期暂不以商业化为开发重点；装扮不能影响游戏数值公平。

首期目标拆成四个验收方向：

| 方向 | 含义 | 验收视角 |
| --- | --- | --- |
| 完整 | 从进入产品到再来一局的主链路没有断点 | 新玩家能在不求助他人的情况下完成一局 |
| 稳定 | 断线、刷新、超时、并发操作不会导致对局卡死或状态错乱 | 异常注入后能恢复到确定状态 |
| 公平 | 胜负只由服务端按统一规则判定，秘密信息不泄露 | 客户端无法改变结果，无法看到无权信息 |
| 在线多人 | 好友房间（以及首期若上线的匹配）能真实完成多人对局 | 多人同时在线完成一局并正确结算 |

游戏核心闭环必须交付的能力：

| 能力 | 范围说明 | 依据 |
| --- | --- | --- |
| 游客身份 | 进入即可玩，凭证可恢复 | 任务书第三节第 4 条 |
| 游戏大厅 | 模式入口与基础信息 | 任务书第三节第 2、3 条 |
| AI 单人对战 | 基础可玩，与真人共用规则引擎，不计入公开竞技排行榜 | 任务书第三节第 3、5 条 |
| 好友在线对战 | 通过分享链接或房间号加入并开局，不要求好友关系 | 任务书第三节第 3、4 条 |
| 房间与邀请 | 创建房间、生成分享链接、房间号加入、座位与准备、开局 | 好友对战的必要载体 |
| 核心牌局 | 服务端权威判定，完整回合流程 | 任务书第三节第 5 条 |
| 异常恢复 | 断线重连、刷新恢复、超时处理 | 任务书第三节第 6 条「稳定」要求 |
| 游戏结算 | 基础胜负与关键信息展示 | 完整对局闭环的必要环节 |

支撑端首期最小能力（不扩大为完整端）：

| 能力 | 首期最小范围 | 首期不包含 | 依据 |
| --- | --- | --- | --- |
| 官网最小版 | 产品介绍、游戏入口、基础帮助、隐私协议入口、基础公告展示 | 公告编排、账号中心、内容社区、多语言 | 任务书第三节第 2 条；首期上线需要入口与说明 |
| 管理后台最小版 | 玩家查询、房间与对局查询、基础公告（展示于游戏端与官网） | 数据看板、批量运营工具、财务结算、对局干预（待 Q19） | 任务书第三节第 2 条；首期运营与故障排查需要 |

关于三端首期的判定：

1. 现有资料确认产品由官网、游戏网页端、管理后台三部分组成，但未明确要求首期三端全部以完整形态交付。
2. 本文的判定：游戏核心闭环必须交付；官网与管理后台只保留最小必要能力，且不得扩大为首期完整端。
3. 理由是缺少官网入口与基础说明会阻断新玩家进入，缺少后台查询会阻断线上故障排查；该判定属于依据产品形态推导，需产品经理评审（Q19、Q20）。
4. 若评审认为支撑端可以延后，可将「官网最小版」「管理后台最小版」整体移入 8.4 首期候选能力，不影响游戏核心闭环的定义。

边界说明：

1. 公开匹配不在首期必须交付层，见 8.4；首期不上线不代表取消该模式。
2. 好友关系链不在首期必须交付层，见 7.4。
3. 成长、排行榜、装扮与商业化不在首期必须交付层，见 8.5。
4. 官网与管理后台首期只做满足产品运行所需的最小能力，具体边界仍待 Q19、Q20 明确。

### 8.5 后续版本能力

说明：下表的排期以第 11 节对应问题的确认结果为准。若某项能力被确认纳入首期，应从本表移出并按首期标准实现。

| 能力 | 说明 | 前置条件 |
| --- | --- | --- |
| 玩家成长 | 等级、任务、成就 | 对局数据稳定、身份可归属 |
| 排行榜 | 公开竞技榜单；AI 局不纳入 | 成长体系与匹配公平性确认 |
| 装扮系统 | 纯外观，不影响数值 | 原创美术资产与角色体系就绪 |
| 好友关系链 | 添加好友、好友列表、关系管理 | 身份体系稳定、社交安全方案就绪 |
| 多语言 | 文案体系与本地化 | 首发地区确认 |
| PWA 增强 | 离线提示、安装引导、通知 | 浏览器兼容范围确认 |

明确约束：成长、排行榜、装扮与商业化没有进入首期规划，不得在开发排期中默认纳入。商业化是否规划本身仍待 Q25，本文不预设结论。

### 8.6 首期范围裁剪原则

1. 影响「一局能否公平打完」的能力优先，影响「玩得久不久」的能力靠后。
2. 任何会新增规则分支的需求，必须先修改规则真源再开发，不允许在实现层临时决定。
3. 视觉与动效可以为稳定性让路，但不能牺牲关键信息的可读性。
4. 首期不为未确认的商业化预留复杂结构，避免过度设计。
5. 首期不做多套并行的房间模型；若公开匹配进入首期，必须与好友房间复用同一套房间与座位模型。

### 8.7 首期成功的定性标准

不设定虚构的量化指标。首期完成后应能满足：

1. 两名好友可以通过链接或房间号完成一局；若首期上线公开匹配，两名互不相识的玩家也应能通过匹配完成一局。
2. 对局过程中任意一方刷新页面或短暂断网，恢复后能继续同一局。
3. AI 与真人在同一张卡上的行为完全一致。
4. 客户端无法获取其他玩家的手牌、先知结果与拆弹位置。
5. 结算结果与服务端记录一致，且能解释胜负原因。

## 9. 产品设计原则

本章分为两类内容：

- 产品层面的目标与约束：必须满足，可作为设计与验收依据。
- 技术实现建议：需要在技术设计阶段验证，不构成已确认的技术方案，也不直接作为验收标准。

### 9.1 游戏公平性

含义：胜负只由规则与服务端判定决定，玩家之间的差异只来自决策与随机，不来自客户端权限或付费。

产品约束：

- 随机结果不能由玩家可控制的客户端决定；具体生成与校验机制属于技术建议，需在技术设计阶段验证。
- 客户端只上报「我想做什么」，不回报「结果是什么」。
- 服务端保存完整权威牌局状态，包括 AI 与其他玩家的隐藏信息。
- 真人客户端只接收当前真人玩家视角的裁剪结果，不得包含 AI 或其他玩家的隐藏信息。
- 不得以「AI 在客户端运行」为由，把 AI 私有手牌或其他隐藏信息下发给真人客户端。
- 装扮与外观不影响任何规则数值。
- 任何后台干预必须留痕、可审计。

验证目标：用被篡改的客户端尝试伪造行动或读取隐藏信息，都必须失败。具体验证方法在技术设计与测试阶段确定。

### 9.2 规则一致性

含义：同一张卡、同一个阶段、同一种情形，在 AI 局、好友局、匹配局中结果完全一致。

产品约束：

- 所有模式与 AI 复用同一套规则定义，不允许出现两套判定口径。
- AI 通过与其他玩家相同的行动接口参与对局，每次行动都经过统一的规则校验。
- AI 行动经统一校验后，由服务端判定并更新最终牌局状态。
- 对局必须能对应到其使用的规则版本；记录方式由技术设计确定。
- 规则变更必须同步更新规则真源、帮助文案与测试用例。
- 不允许在 UI 层补偿规则差异。

验证建议（技术设计阶段确认具体方法）：同一组随机种子与行动序列，在不同模式下产生相同结果。该方式属于可复现性验证建议，不构成已确认的技术方案。

### 9.3 多人实时体验

含义：多人同时操作时，每个人都能及时、准确地知道当前局面。

产品约束：

- 明确「谁的回合、还剩几次行动、正在等待谁响应」。
- 关键状态变化要有即时反馈，不能只依赖玩家自己观察。
- 对网络延迟有容忍设计，不因短暂延迟判定玩家违规。
- 并发操作必须有确定、可解释的处理顺序；具体排序与同步机制属于技术建议，需在技术设计阶段验证。
- 等待他人时有可感知的进度，避免「卡住了」的错觉。

### 9.4 操作简单易懂

含义：新玩家无需阅读长文档即可完成第一局。

说明：本节涉及的数量与时长均为产品假设与设计目标，需通过可用性测试验证，不作为首期验收指标。

产品约束：

- 首屏到开局的主要决策尽量控制在三个以内（设计目标，待验证）。
- 关键操作有清晰的可点区域与禁用原因。
- 新手引导优先内嵌在对局中，而不是前置教程墙。
- 规则说明随时可查，且与当前局面相关。
- 破坏性操作（如放弃、退出）需要二次确认。

### 9.5 异常状态可恢复

含义：断网、刷新、切后台、超时、误操作都不会让玩家永久失去对局。

产品约束：

- 身份凭证可恢复，丢失后有明确的重取路径。
- 对局状态以服务端为权威；客户端在异常后必须能恢复到该权威状态。快照、事件回放等均为技术建议，需在技术设计阶段验证。
- 异常恢复过程中不得出现重复出牌、重复抽牌等结果；幂等是候选实现手段，不作为已确认方案。
- 超时与断线有明确的托管或等待策略（策略待确认 Q05–Q07）。
- 异常恢复后，玩家能看懂离开期间发生了什么。

### 9.6 原创美术和品牌

含义：产品形象完全自有，不依赖竞品的视觉资产与品牌联想。

具体要求：

- 名称、Logo、角色、卡面、图标、动效、音效、文案全部原创或已获授权。
- 不模仿竞品的角色造型、配色体系与标志性构图。
- 建立素材授权台账，记录每个资产的来源与授权范围。
- 视觉规范先于批量产出，避免后期返工。
- 对外宣传不使用竞品名称作为卖点。

### 9.7 可扩展性

含义：后续增加模式、卡牌、成长与装扮时，不需要推翻核心结构。

产品约束：

- 规则、房间、结算的数据结构预留版本与扩展位，但不做无依据的过度设计。
- 当前可用模式尽量复用同一套牌局与房间模型，具体复用方式在技术设计中确定。
- 客户端界面应能随权威状态稳定更新，具体组织方式属于技术建议。
- 新增内容优先通过配置与数据扩展（技术建议，需验证可行性），不修改规则内核。
- 扩展必须以不破坏现有公平性为前提。

### 9.8 数据最小化与合规

含义：只收集产品运行所必需的信息，并满足首发地区的合规要求。

具体要求：

- 游客阶段默认不收集手机号、身份证等敏感信息；若首发地区法规要求实名，按 Q23 的法务结论在对应环节补充。
- 明确告知玩家收集了什么、用于什么。
- 对局数据与身份数据的保留期限可配置（期限待确认 Q17、Q23）。
- 提供隐私政策与用户协议入口。
- 首发地区的实名、防沉迷、版号等要求以法务结论为准，不在本文预设。

## 12. 产品风险与注意事项

### 12.1 风险清单

下表中的缓解措施属于建议，需在立项与技术设计阶段验证，不构成已确认方案。

| 编号 | 风险 | 具体表现 | 影响 | 缓解措施 | 责任方 |
| --- | --- | --- | --- | --- | --- |
| R01 | 原创化与知识产权风险 | 名称、角色、卡面、UI 布局与竞品过于接近；美术素材来源不清 | 上线被投诉、下架或诉讼；被迫重做视觉资产 | 立项阶段完成名称与商标排查；建立素材授权台账；视觉规范先于批量产出；调研只记录机制不复制素材 | 产品、法务、美术 |
| R02 | 在线多人实时同步风险 | 延迟导致状态不一致；并发操作顺序错乱；动画与真实状态脱节 | 玩家看到错误局面，产生争议与流失 | 服务端掌握权威状态；并发处理与同步机制在技术设计中验证并准备回退方案；异常时以权威状态纠正客户端 | 技术、产品 |
| R03 | 服务端规则判定风险 | 规则实现有偏差；不同模式判定不一致；规则变更后旧对局异常 | 公平性受损，无法解释胜负，测试成本上升 | 规则定义单一来源；随机种子复现作为验证建议；对局关联规则版本；18 条验收用例纳入自动化 | 技术、策划、测试 |
| R04 | 游客身份丢失风险 | 清缓存、换设备、浏览器隐私模式导致身份无法找回 | 玩家丢失进度与装扮，客服压力大，口碑受损 | 首期定义可恢复凭证方案；提供恢复码或绑定入口；对高风险操作提前提示 | 产品、技术 |
| R05 | 网络中断与异常退出风险 | 断线、切后台、来电、主动退出导致对局卡住或误判 | 其他玩家被迫等待，对局无效，体验崩坏 | 明确保留时间与超时策略；重连回到原座位；异常退出有确定处理结果；对局可安全终止 | 产品、技术 |
| R06 | 产品范围过大导致周期失控 | 官网、游戏端、后台、三种模式、成长、装扮同时推进 | 首期迟迟不能上线，质量下降，团队信心受损 | 按第 8 节锁定首期范围；范围变更需评审；成长与装扮明确后置；首期不做商业化 | 产品负责人 |
| R07 | 合规风险 | 未取得必要资质；未成年人保护缺失；隐私政策不完整 | 无法上线或被要求整改 | 立项阶段确认首发地区要求；数据最小化；协议与隐私入口前置；法务提前介入 | 产品、法务 |
| R08 | 玩法同质化与预期偏差 | 玩家认为产品是竞品替代品；或在没有竞品符号后失去辨识度 | 传播效率低，品牌难以建立 | 建立自有角色与视觉叙事；传播强调原创品牌；用差异化体验（网页即开、规则透明）建立记忆点 | 产品、美术、市场 |
| R09 | 公开匹配冷启动风险 | 在线人数不足导致长时间匹配不到 | 玩家判定产品「没人玩」而流失 | 若首期不上线匹配，以房间码承接开局；若上线，需准备 AI 补位（Q08）或缩短等待的策略；匹配超时有明确出口 | 产品、运营 |
| R10 | 规则未决项拖累开发 | 攻击卡模式、超时策略等未定就开工，实现反复推翻 | 返工、测试用例失效 | 第 11 节问题在对应 PRD 前必须闭环；未确认项不得由开发自行决定 | 产品经理 |

### 12.2 风险优先级

| 优先级 | 风险 | 理由 |
| --- | --- | --- |
| 最高 | R01 知识产权、R06 范围失控 | 前者可能导致产品无法上线，后者会让首期无法交付 |
| 高 | R02 实时同步、R03 服务端判定、R05 异常退出 | 直接决定「稳定、公平」两个首期目标能否成立 |
| 中 | R04 游客身份、R09 匹配冷启动、R07 合规 | 影响留存与上线资格，可在立项阶段并行解决 |
| 中低 | R08 同质化 | 影响长期品牌，不阻断首期交付 |

### 12.3 需要持续跟踪的事项

1. 规则真源与在线形态的差异是否会随时间扩大，是否需要发布 v2.0。
2. 第 11 节待确认项的关闭进度，是否阻塞对应 PRD。
3. 原创美术资产的产出节奏是否匹配首期时间点。
4. 首期范围是否发生未经评审的扩张。
