## 4. 规则文件与在线多人目标之间的冲突

规则规格在 [第 1 节](file:///Users/macmima1234/Documents/Temp-BoomCat/GAME_RULES_SPEC.md#L36-L43) 把「在线多人 / 房间 / 服务器权威」「账号」「内购」明确列为**非目标**，并在 [第 0 节](file:///Users/macmima1234/Documents/Temp-BoomCat/GAME_RULES_SPEC.md#L13-L13) 要求「单页、纯前端、无后端、无账号」。而本次目标包含官网、网页端、管理后台，以及好友在线对战、公开匹配。两者不是细节差异，而是产品形态级别的冲突。

| 编号 | 冲突点 | 规则文件现状 | 目标产品要求 | 影响 |
| --- | --- | --- | --- | --- |
| C1 | 是否存在服务端 | 第 1 节：非目标含「服务器权威」；第 0 节：纯前端、无后端 | 在线对战、公开匹配、管理后台、排行榜均需要服务端 | 规则文档的启动指令不能直接用于联机版本，需重写执行环境约束 |
| C2 | 账号体系 | 第 1 节：账号列为非目标 | 流程图已有「获取或恢复游客身份」；排行榜、成长、装扮需要身份 | 需新增身份与数据归属设计，规则文档不覆盖 |
| C3 | 秘密信息保护 | 第 11.2 节用「交接屏」「不留在 DOM 可见状态」保护手牌、先知结果、拆弹位置 | 联机下客户端持有全部状态即可被查看，必须服务端下发裁剪后的视图 | 现有保密方案只适用于同屏/单机，联机需服务端权威 + 视图裁剪 + 防作弊 |
| C4 | AI 运行位置 | 第 11.1 节 AI 为本地启发式，第 11 节默认单机 | 联机 AI 局若在客户端跑 AI，AI 可读到玩家手牌；排行榜场景还可被篡改 | 需确认 AI 局是否服务端化，直接影响架构与成本 |
| C5 | 回合时序与计时 | 第 2 节 `nopeWindowTimeoutMs = 5000` 由本地计时，AI「一律立即 pass」 | 联机需要服务端权威倒计时、断线托管、超时自动 pass | 时序权威归属未定义，现有状态机是单机主循环模型 |
| C6 | 人数与开局 | 第 4 节固定 2–5 人，爆炸猫数 = 人数 − 1，牌库 31–43 张 | 公开匹配需定义匹配人数、人数不足时的补位或 AI 补位 | 人数策略会影响开局、牌库、等待时长 |
| C7 | 断线与重连 | 规则文档无此概念 | 在线对战必须处理断线、重连、中途退出、托管 | 状态机缺少「玩家离线」「暂停」「放弃」等状态 |
| C8 | 弃牌堆公开 | [第 7 节](file:///Users/macmima1234/Documents/Temp-BoomCat/GAME_RULES_SPEC.md#L220-L220) 明确弃牌堆内容对所有玩家公开 | 联机需向所有客户端同步弃牌堆；同时要防止通过同步包泄露手牌 | 同步协议需区分公开区与私有区 |
| C9 | 随机数 | [第 11.2 节](file:///Users/macmima1234/Documents/Temp-BoomCat/GAME_RULES_SPEC.md#L353-L353) 要求 seeded RNG 便于复现 | 联机洗牌、随机抽牌不能在客户端产生 | seed 生成与保管需服务端负责，客户端只做动画 |
| C10 | 交付端数量 | 第 0 节要求「单页」游戏 | 官网、游戏端、管理后台三个交付端 | 工程结构、路由、鉴权、发布流程都需重新定义 |
| C11 | 扩展与元系统 | 第 1 节扩展包为非目标 | 目标包含角色与装扮、成长系统；竞品形态待调研 | 装扮是否影响数值、是否属于扩展内容，需产品定调 |
| C12 | 交付节奏 | 第 0 节要求一次性交付数据模型到 UI 并跑通验收用例 | 本阶段明确不开发 | 启动指令与当前阶段指令冲突，需以本阶段任务书为准 |

## 6. 当前项目最大的技术与产品风险

### 6.1 技术风险

| 等级 | 风险 | 说明 | 缓解方向 |
| --- | --- | --- | --- |
| 高 | 联机权威架构缺位 | 现有规则与状态机是为「纯前端单机」设计的主循环模型，没有服务端、指令同步、视图裁剪、重连快照的概念 | 立项后先定「规则引擎与传输层解耦」的架构，规则内核可在前后端复用 |
| 高 | 秘密信息泄露 | 手牌、先知顶 3 张、拆弹插入位置一旦下发到客户端即可被查看；现有方案只靠 UI 遮挡 | 服务端只下发玩家视角状态；敏感随机在服务端产生 |
| 高 | 需求范围过大 | 官网 + 游戏端 + 后台，三种模式、成长、装扮、排行榜，任何一项都可独立成项目 | 首版做减法，先锁定「单局可玩 + 一种联机模式」 |
| 中 | 规则内核与 UI 耦合 | 规则文档明确要求「状态结算与动画分离」，但尚无实现验证 | 规则引擎做成纯函数状态机，动画只消费事件流 |
| 中 | 断线重连与状态同步 | 需要事件日志、快照、幂等重放；规则文档未定义 | 在设计阶段引入对局事件日志与版本号 |
| 中 | 可复现性 | seed 由客户端产生则无法审计，由服务端产生则需保存与回放机制 | seed 服务端生成并随对局存档 |
| 中 | AI 实现成本 | `hard` 难度需要记牌与概率估算，且联机下必须在服务端运行 | 首版只做 `easy` / `normal`，`hard` 延后 |

### 6.2 产品风险

| 等级 | 风险 | 说明 | 缓解方向 |
| --- | --- | --- | --- |
| 高 | 规则与目标不一致导致返工 | 规则文档明确排除联机、账号、服务端，而目标是联机产品 | 立项阶段一次性确认第 5 节全部问题，再更新规则文档版本 |
| 高 | IP 与合规风险 | 名称、角色、卡面、UI 布局均可能涉及他人在先权利；国内上线还涉及版号与实名 | 尽早启动名称与商标排查，美术从概念阶段就做原创化 |
| 中 | 对标过深导致同质化 | 目标是「完整对标产品体验」，容易在交互与视觉上过度接近竞品 | 调研只记录机制与体验结论，不复制布局与素材，另立设计语言 |
| 中 | 原创美术成本不可控 | 卡牌 56 张、角色、装扮、动效都需要原创资产 | 先定美术规范与最小可用资产集，再评估外包或分批产出 |
| 中 | 留存依赖元系统 | 排行榜、成长、装扮尚无设计，可能影响首版留存 | 首版明确元系统是否在范围内，避免「玩法做完才发现没有留存闭环」 |
| 中 | 公开匹配冷启动 | 匹配依赖在线人数，早期可能长时间匹配不到 | 设计 AI 补位或房间码优先策略，但这属于新规则，需产品决策 |

### 6.3 项目管理风险

- 本阶段只有方向性目标，没有验收标准与范围边界，容易被理解为「三端全量交付」。
- 规则文档的启动指令要求「按顺序交付数据模型到 UI」，与当前「只做调研、不开发」的指令冲突，需要以任务书为准并显式记录。
- `images/mermaid-核心业务流程.png` 尚未纳入 Git，属于唯一的产品流程依据，存在丢失风险。

## 7. 结论

1. 项目当前处于「规则已成型、产品未立项」的阶段：单局玩法有可直接编码的规格，但产品形态、账号、联机、后台、美术全部空白。
2. 规则文档与目标产品存在 12 处系统性冲突，核心是「纯前端单机」与「服务端权威联机」的架构分叉，不能靠局部修改规则解决。
3. 在 Q1–Q15 得到答复前，不建议进入原型、UI 或技术设计；否则返工概率高。
4. 竞品调研可以立即启动，且应严格区分「可观察事实」与「推测」，调研结论用于形成 BOMB CAT 自己的设计决策，而不是复制竞品。
