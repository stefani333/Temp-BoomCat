## 0. 结论摘要

1. 当前工程是「浏览器即服务端」的单机架构：`packages/game-core` 规则引擎随前端打包，在浏览器内运行，`GameState` 全量存在于页面内存，并以完整快照写入 `localStorage`。这是多人联机前最核心的架构差距。
2. 规则引擎本身是纯 TypeScript、无 React 与 DOM 依赖，校验逻辑集中在一个 `apply` 入口，具备迁移到 Node.js 服务端的基础。但存在三处必须先处理的工程问题：包只导出 TS 源码、`state` 公开可变且失败也会消耗操作 ID、模拟玩家在决策阶段消耗权威随机数。
3. 视图裁剪 `getGameView(engine, viewerId)` 已按玩家生成独立视图，隐藏信息裁剪逻辑与规则第 7 节一致；服务端化后可直接复用，但缺少「连接身份与 viewerId 绑定」这一信任边界。
4. 房间层只是单机占位：房间 ID 固定、玩家 ID 按座位生成、无退出、无断线、无房主转移、无解散投票、无房间号分配、无生命周期管理。规则 12.5 至 12.8 要求的房间行为全部未实现，需要重新设计，而不是改造。
5. 多人联机能力 15 项中：0 项已具备，7 项部分具备，8 项尚未实现。没有可以直接复用的联机基础设施；超时处理本身未实现，其口径另需产品确认（第 10 节 D-07、D-12）。
6. 推荐方向：新增独立的 Node.js + TypeScript 房间服务，复用 `game-core` 作为唯一规则判定者，新增 `packages/room-core` 承载房间状态机，WebSocket 下发「按玩家裁剪的视图」，MySQL 或 PostgreSQL 持久化房间与动作日志，首期不引入 Redis。具体框架、数据库、实时通道均为候选方案，需产品负责人批准，见第 10 节。
7. 未发现阻断性规则缺陷。存在 1 项必须由产品负责人裁决的规则口径冲突：规则 12.4（起始玩家由房主指定、未指定不得开始）与已确认记录 Q-08（自动确定起始玩家、移除指定入口）不一致，当前代码按 Q-08 实现。

## 3. 规则引擎服务端复用评估

### 3.1 六项问题的结论

| 编号 | 问题 | 结论 | 主要依据 |
| --- | --- | --- | --- |
| Q1 | 能否直接在 Node.js 服务端运行 | 源码层面可以，工程层面需改造 | 无 DOM/React 依赖；但包只导出 TS 源码，`build` 不产出 JS |
| Q2 | 是否依赖浏览器 API、React 或浏览器全局对象 | 否 | 全目录检索仅命中 `structuredClone` 与 `Math.random` 各一处 |
| Q3 | 能否让服务端成为唯一状态修改者 | 设计上可以，当前实现需封装 | 单一 `apply` 入口；但 `state` 公开可变，`GameView` 由调用方指定 viewerId |
| Q4 | 是否存在客户端绕过规则修改状态的路径 | 当前形态下必然存在 | 引擎打包进前端；`playerId` 由请求方填写；完整状态写入 localStorage |
| Q5 | 如何针对不同 playerId 生成独立 GameView | 已具备 | `getGameView(engine, viewerId)` 按查看者裁剪 |
| Q6 | 随机数机制是否适合服务端权威执行与对局恢复 | 基本适合，需处理种子来源与模拟玩家消耗 | `rngState` 存于状态、可序列化；mulberry32 确定性可复现；默认种子与模拟决策存在副作用 |

### 3.2 逐项证据

#### Q1 与 Q2：运行环境依赖

检索 `packages/game-core/src` 中的 `window`、`document`、`localStorage`、`sessionStorage`、`fetch`、`WebSocket`、`navigator`、`React`、`setTimeout`、`crypto`、`performance`，全部无命中。仅有两处需要说明：

- `packages/game-core/src/engine.ts:117`：`structuredClone(this.state)`，用于测试分支 `fork()`。Node.js 17 及以上原生支持，不构成浏览器依赖。
- `packages/game-core/src/engine.ts:45`：未传种子时使用 `Math.floor(Math.random() * 0xffffffff)`。`Math.random` 在 Node 中同样存在，但作为权威对局的种子来源不合适，应由服务端生成强随机种子后显式传入。

工程层面的阻碍：

- `packages/game-core/package.json` 的 `exports` 为 `"./src/index.ts"`，`build` 脚本为 `tsc --noEmit`，`noEmit` 见 `tsconfig.json`。也就是说该包没有可被 Node 直接加载的 JS 产物。服务端要么引入 `tsx`/`ts-node` 一类加载器，要么为该包增加 `tsup` 构建。后者更稳妥，也符合 `AGENTS.md` 对库构建工具 `tsup` 的约定。
- `tsconfig.json` 的 `lib` 包含 `DOM`，但代码未使用 DOM 符号。服务端化时建议为服务端构建单独配置 `lib: ["ES2022"]`，从类型层面阻断浏览器 API 误用。

#### Q3：单一状态修改者

- 所有状态变更集中在 `GameEngine.apply`（`packages/game-core/src/engine.ts:148-182`），页面不直接改状态，只通过 `App.tsx:56-67` 调用 `apply`。这一点符合服务端权威的设计方向。
- 但 `state` 是公开可变属性（`engine.ts:104`），构造函数接受任意 `GameState` 且不做校验（`engine.ts:106-108`，前端恢复快照即 `App.tsx:156` 直接 `new GameEngine(savedSnapshot.state)`）。服务端必须把状态封装到房间实例内部，禁止跨模块直接写。
- `apply` 先记录 `actionId` 与累加 `stepCount`，再进入分支校验（`engine.ts:149-155`）。这意味着被拒绝的操作也会修改状态并占用操作 ID，属于服务端化前必须修正的语义。

#### Q4：客户端绕过路径

当前形态下存在，且是结构性的，不是实现疏漏：

1. 引擎与完整状态运行在浏览器内。`App.tsx:41` 持有 `engineRef`，任何使用开发者工具的人都可以读取或改写 `engineRef.current.state`。
2. `GameAction` 的 `playerId` 由调用方填写（`types.ts:96-114`），引擎只校验「是否轮到你」，不校验「你是不是这个玩家」（如 `engine.ts:274`、`engine.ts:514`）。服务端化后如果直接信任请求体里的 `playerId`，任何人都可以替别人行动。
3. `getGameView(engine, viewerId)` 的 `viewerId` 由调用方给出（`view.ts:73`），没有身份校验。任何客户端只要知道别人的 playerId，就能生成别人的视图。
4. `apps/game-web/src/storage.ts:84-88` 将完整 `GameState`（所有人的手牌、抽牌堆顺序、随机数状态）序列化进 `localStorage`，键名 `bombcat:game-snapshot:v1`（`storage.ts:17`）。本机任何脚本都能读取。单机 MVP 中对手都是模拟玩家，影响有限；联机后这是直接泄露隐藏信息。
5. `DemoScreen.tsx` 在浏览器内运行 `runFullSimulation`，说明完整规则判定能力确实随前端分发。这本身不是问题，但意味着「代码在前端」不能作为任何权威依据。

#### Q5：按玩家生成独立视图

`getGameView` 已实现按查看者裁剪（`packages/game-core/src/view.ts:73-156`）：

- `myHand` 只返回查看者手牌（`view.ts:133`）。
- 其他玩家只输出 `handCount`（`view.ts:121-131`）。
- 预见未来三张牌仅在 `pending.sourcePlayerId === viewerId` 时写入 `seenCards`（`view.ts:96-98`）。
- 事件日志过滤 `privateTo`（`view.ts:150-152`）。
- 抽牌堆只输出数量 `drawPileCount`（`view.ts:145`），不输出顺序。
- 弃牌堆输出明细（`view.ts:146`），符合规则第 7 节「弃牌堆公开」。
- 炸弹放回位置不进入任何事件（`engine.ts:608` 只记录「已秘密放回」），视图也不含位置。

结论：视图裁剪逻辑可以直接复用到服务端，服务端应「每个连接只收到自己的视图」，并且 `viewerId` 必须来自服务端会话而不是请求参数。

#### Q6：随机数机制

- 算法为 mulberry32，状态保存在 `GameState.rngState`（`types.ts:91`），实现见 `packages/game-core/src/rng.ts:5-33`。洗牌、抽牌、随机抽手牌、炸弹放回位置、模拟决策都走同一状态。
- 确定性可复现：测试「相同种子与策略可复现对局结果」通过（`rules.test.ts:605-611`）。
- 对局恢复：只要持久化完整 `GameState`（含 `rngState`），可以从任意一步继续。仅靠「初始种子 + 动作序列」恢复则不可靠，原因是模拟玩家在决策阶段消耗随机数（见下一条）。
- 两点必须在服务端化前处理：
  1. 默认种子来自 `Math.random`（`engine.ts:45`），服务端应改为显式传入密码学随机种子并记录，便于复盘与防预测。
  2. `nextBotStep` 在生成动作时就调用 `nextRandom(state)` 推进权威随机状态（`bots.ts:79`、`84`、`97`、`110`、`127`、`139`、`143`、`147`、`159`、`216`），而动作真正提交前状态已被改动。单机表现为「随机流提前前进」，服务端表现为「失败的决策也会污染随机流」。若联机阶段保留模拟玩家或机器人补位，必须先改造为「决策不消耗状态随机数」。

### 3.3 服务端化所需引擎改造（不改变规则语义）

以下为工程改造建议，均不涉及规则变更：

| 编号 | 改造点 | 目的 |
| --- | --- | --- |
| E-01 | 为 `game-core` 增加 `tsup` 产物与 `exports` 指向 `dist`，或服务端使用 TS 运行器 | 让 Node 可直接加载 |
| E-02 | 将 `state` 改为只读访问（`getState(): Readonly<GameState>` 或快照），禁止外部直接改写 | 保证服务端是唯一写入者 |
| E-03 | `apply` 先校验后记账：失败不写入 `processedActionIds`、不累加 `stepCount` | 修正幂等语义，避免失败被重试当成成功 |
| E-04 | `processedActionIds` 改为有界去重（按玩家保留最近 N 条或落库唯一索引） | 防止状态无限膨胀 |
| E-05 | 新增 `stateVersion`（每次成功操作加 1），与 `stepCount` 分离 | 供同步、乱序丢弃与断线补齐 |
| E-06 | 随机种子由服务端生成并记录；模拟玩家决策改为不消耗权威随机数 | 可复现、可审计 |
| E-07 | 为 `GameState` 增加 schema 版本与校验函数 | 服务重启恢复与快照迁移 |
| E-08 | 构造函数拒绝未通过校验的状态 | 防止伪造快照直接进入对局 |

## 6. 后端技术选型对比

说明：本章为调研与建议，不构成已批准选型。任务书列出的 Node.js + NestJS、WebSocket、MySQL、Redis 均为候选，最终以产品负责人确认为准。

### 6.1 运行时与语言

| 方案 | 优点 | 缺点 | 复杂度 | 首期必要性 |
| --- | --- | --- | --- | --- |
| Node.js + TypeScript | 与 `game-core` 同语言，可直接复用规则与类型；团队已有 pnpm/TS 工具链；单房间低并发场景足够 | 单线程，CPU 密集计算会阻塞；需要进程守护与重启恢复 | 低 | 高 |
| Go / Rust 重写规则 | 性能与内存控制更好 | 规则需要重写或双实现，违反「同一套卡牌定义」原则，回归成本高 | 高 | 低 |

结论：Node.js + TypeScript 是唯一能零规则重写复用现有引擎的路线，建议采用。Go/Rust 不进入首期评估范围。

### 6.2 后端框架

| 方案 | 优点 | 缺点 | 复杂度 | 首期必要性 |
| --- | --- | --- | --- | --- |
| MidwayJS（AGENTS.md 既定 Web 业务层） | 与团队规范一致；TypeScript 原生；依赖注入、生命周期、配置体系完整；可与 TypeORM 配合 | 实时房间循环仍需自建；框架抽象较重，调试链路长 | 中 | 中高 |
| NestJS（任务书候选） | 生态成熟，WebSocket Gateway、Guard、Pipe 概念清晰；模块划分适合房间/对局/身份 | 与 AGENTS.md 既定技术栈不一致；装饰器与 DI 增加心智负担 | 中 | 中 |
| Fastify / Express（轻量） | 启动快、依赖少、路由与 WS 集成直接；适合以房间循环为核心的服务 | 需要自行约定目录、校验、错误处理；团队长期维护规范需补齐 | 低 | 中 |

结论：若严格遵守 `AGENTS.md`，首选 MidwayJS；若以「最小可用联机服务」为目标，Fastify 更轻。NestJS 可作为备选。三者都需要新增 `apps/game-server` 与 `packages/room-core`，框架选择不改变分层。

### 6.3 实时通道

| 方案 | 优点 | 缺点 | 复杂度 | 首期必要性 |
| --- | --- | --- | --- | --- |
| 原生 WebSocket（如 `ws`） | 协议可控、消息体积小、易于定义版本与请求序号；Nginx 直接反代 Upgrade | 需自行实现心跳、重连、房间广播、消息校验 | 中 | 高 |
| Socket.IO | 内置房间、重连、心跳、ACK、降级；开发效率高 | 协议自有两层封装，版本升级需前后端同步；体积更大；与「显式协议版本」目标存在冗余 | 中 | 中 |
| HTTP 轮询 / SSE | 实现简单、代理兼容好 | 延迟与请求量不理想；服务端推送需额外设计；不适合高频对局同步 | 低 | 低 |

结论：两种均可满足 2–5 人房间。若团队希望完全掌控协议与审计字段，选原生 WebSocket；若优先开发速度与重连能力，选 Socket.IO。属产品/架构决策，见 D-04。

### 6.4 数据库

| 方案 | 优点 | 缺点 | 复杂度 | 首期必要性 |
| --- | --- | --- | --- | --- |
| MySQL 8 | 运维普及、托管方案多；事务满足房间与动作日志 | JSON 能力弱于 PostgreSQL；复杂状态查询不便 | 中 | 高（若选此方案） |
| PostgreSQL | `AGENTS.md` 数据存储首选；JSONB 适合存状态快照与事件；唯一索引可做幂等 | 团队需确认运维与备份方案 | 中 | 高（若选此方案） |
| 仅内存 + 定期文件快照 | 零数据库依赖，首期最快 | 重启丢数据、无法多实例、无法审计 | 低 | 低（不满足 G-11、G-12） |

结论：联机阶段必须持久化，内存方案不满足「服务端重启恢复」。数据库选型与 `AGENTS.md`（PostgreSQL 首选）存在一致性理由，任务书候选为 MySQL，需产品负责人明确，见 D-03。数据模型建议：`rooms`、`room_players`、`games`（当前状态快照 + 版本）、`game_actions`（动作日志 + 幂等唯一键）。

### 6.5 Redis 是否首期必需

| 用途 | 首期是否需要 | 说明 |
| --- | --- | --- |
| 房间热状态缓存 | 不需要 | 单实例下进程内存即可，房间数量有限 |
| 分布式锁 / 单房间串行化 | 不需要（单实例） | 进程内房间队列即可；多实例时必须 |
| 跨实例广播（Pub/Sub） | 不需要（单实例） | 多实例或滚动发布时必须 |
| 解散投票 2 分钟定时 | 不需要 | 进程内定时器 + 数据库落盘即可；重启后需恢复扫描 |
| 会话 / 重连票据 | 可选 | 首期可用签名令牌，不依赖 Redis |

结论：首期非必需。引入条件是多实例部署、滚动发布或需要跨进程共享房间状态。建议明确写入架构约束：**首期单实例，房间状态以进程内存为热数据、数据库为持久化**，避免过早引入 Redis 增加运维面。

### 6.6 服务端部署方式

| 方案 | 优点 | 缺点 | 复杂度 | 首期必要性 |
| --- | --- | --- | --- | --- |
| 单机 systemd 守护 Node 进程 + Nginx 反代 | 与现有服务器形态一致；改动最小；日志走 journald 或文件 | 无自动扩缩容；发布需重启；单点 | 低 | 高 |
| Docker / Compose | 环境一致、易回滚 | 需要服务器安装 Docker；与现有裸机 Nginx 并存需规划 | 中 | 中 |
| K8S | 弹性与滚动发布 | 对 2–5 人房间严重过度设计 | 高 | 低 |

结论：首期建议沿用现有 Ubuntu + Nginx，新增 `/api` 与 `/ws` 反向代理与 systemd 守护；容器化可作为后续演进。

### 6.7 日志、监控与异常处理

| 项目 | 建议 | 首期必要性 |
| --- | --- | --- |
| 结构化日志 | JSON 行日志，字段含 `roomId`、`gameId`、`playerId`、`actionId`、`stateVersion`、结果码 | 高 |
| 动作审计 | 每次成功操作落 `game_actions`，隐藏信息不落公开日志 | 高（规则 8.3） |
| 业务错误 | 校验失败作为正常响应返回错误码，不抛异常、不断连接 | 高 |
| 未捕获异常 | 进程级兜底，标记房间异常并停止接受新动作，避免带病结算 | 高 |
| 健康检查 | HTTP `/healthz` 返回进程与数据库连通状态 | 高 |
| 指标 | 房间数、连接数、动作耗时、失败率、重连次数 | 中 |
| 告警 | 进程退出、数据库不可用、错误率阈值 | 中 |

### 7.2 需要记录的细节

- `PendingView.drawnBomb` 对全部查看者下发（`view.ts:99`）。炸弹猫被抽到属于公开事件（`engine.ts:525` 写入公开日志），炸弹牌本身不含额外隐藏信息，判定为可接受，但应在协议文档中显式声明为公开字段。
- `privateTo` 机制已存在（`types.ts:66-71`、`engine.ts:135-142`、`view.ts:150-152`），但当前没有任何 `logEvent` 调用传入该参数。预见未来改用 `pending.seenCards` 承载，未走私有日志。后续若增加私有事件，必须显式传入 `privateTo`，否则会下发给所有人。
- `processedActionIds`、`rngState`、`drawPile` 都属于服务端内部字段。服务端只允许下发 `GameView`，禁止直接序列化 `GameState`。
- 视图裁剪是「不发送」，不是「不允许知道」。只要完整状态进入客户端，裁剪就失去意义。因此「引擎不下发」比「视图裁剪正确」更关键。

### 7.3 当前形态下已存在的泄露与绕过路径

按严重程度排序：

1. 完整状态写入 `localStorage`（`storage.ts:84-88`），包含所有玩家手牌与抽牌堆顺序。联机后必须在客户端停止保存完整状态。
2. 浏览器内存中的 `engineRef.current.state` 可被任意读取与改写（`App.tsx:41`）。联机后客户端不应包含规则执行所需的完整状态。
3. `playerId` 无会话绑定（`types.ts:96-114`、`engine.ts:274`），可替他人行动。
4. `viewerId` 无认证（`view.ts:73`），可生成他人视图。
5. 恢复快照时构造引擎不做校验（`App.tsx:156`、`storage.ts:36-50` 仅浅层字段判断），篡改快照可直接进入任意状态。

### 7.4 服务端化必须补齐的安全措施

| 编号 | 措施 | 对应风险 |
| --- | --- | --- |
| S-01 | 连接建立时签发房间内身份票据，服务端维护 `connectionId → playerId` 映射，动作不接受请求体中的 `playerId` | 代操作 |
| S-02 | 每次推送只序列化 `getGameView(engine, sessionPlayerId)`，服务端日志中禁止打印 `GameState` | 隐藏信息泄露 |
| S-03 | 客户端移除对完整状态的持久化；只保留界面偏好与重连票据 | 本地泄露 |
| S-04 | 恢复对局前校验状态结构与 schema 版本，拒绝非法快照 | 伪造状态 |
| S-05 | 幂等键绑定 `playerId + actionId`，且仅在成功后记录 | 重放与误判成功 |
| S-06 | 动作入口做连接级限流与请求序号校验 | 刷请求 |
| S-07 | 日志字段白名单，隐藏信息与抽牌堆顺序不落公开日志 | 审计泄露 |
| S-08 | 断线重连使用一次性、短时效票据，禁止用 `playerId` 直接重连 | 冒名重连 |

### 7.5 结论

规则第 7 节的要求在「视图函数」层面已经落实，并有自动化用例。真正的安全缺口不在视图函数，而在执行位置与身份信任：只要引擎和完整状态在客户端，视图裁剪就只是防误看，不是防作弊。服务端化的核心目标应当写成一句话：**完整状态永不离开服务端，客户端只收到自己的视图与公开事件。**

## 11. 最终建议架构方向

本章为建议，不代替产品决策。所有结论均以「规则引擎不改语义、服务端唯一权威、隐藏信息不出服务端」为前提。

### 11.1 目标拓扑

```text
浏览器（游戏端 / 后续小程序）
   │  HTTPS（静态资源）         WSS（房间与对局）
   ▼                              ▼
Nginx（现有服务器）
   ├─ /           静态前端
   ├─ /api/*      反向代理 → Node 服务
   └─ /ws         Upgrade → Node 服务
                         │
                         ▼
                 apps/game-server
                 ├─ 连接与身份会话
                 ├─ 房间状态机（packages/room-core）
                 ├─ 规则判定（packages/game-core，唯一实例写入）
                 ├─ 视图裁剪（getGameView）
                 └─ 持久化（rooms / games / game_actions）
                         │
                         ▼
                 数据库（PostgreSQL 或 MySQL，待定）
```

### 11.2 模块划分

| 模块 | 职责 | 与现有代码关系 |
| --- | --- | --- |
| `packages/game-core` | 规则判定、状态与视图 | 复用，仅做工程改造 E-01 至 E-08，不改规则 |
| `packages/room-core`（新增） | 房间状态机：创建、加入、准备、开始、退出、断线、房主转移、解散投票、生命周期 | 纯 TS，无 IO，便于单测；不放进 `game-core`，避免规则包承担房间职责 |
| `apps/game-server`（新增） | HTTP 与 WebSocket 传输、会话与票据、房间编排、持久化、定时器、日志 | 仅此层接触数据库与网络 |
| `apps/game-web` | 渲染视图、提交动作、断线重连、错误提示 | 去掉本地引擎与完整状态持久化，改为服务端视图驱动 |

分层原则：传输层不写规则，房间层不写规则，规则层不碰网络与存储。

### 11.3 通信协议建议

- 动作请求：`{ v, type, reqId, roomId, payload }`。`playerId` 不由客户端提供，由服务端会话注入。
- 动作响应：`{ reqId, ok, code, message, stateVersion }`。业务校验失败返回错误码，不断开连接。
- 状态推送：`{ stateVersion, view, events }`，每个连接只收到自己的 `GameView` 与公开事件。
- 断线重连：客户端携带重连票据请求 `resume`，服务端校验身份后下发当前 `view` 与缺失的公开事件。
- 协议版本 `v` 用于后续兼容；未识别版本直接拒绝并提示升级。

### 11.4 身份、断线与重连

- 创建或加入房间时签发房间内身份票据，票据与会话绑定，服务端维护 `connectionId → playerId`。
- 断线只更新连接状态，不移除玩家、不改变准备状态、不跳过座位，符合规则 12.5。
- 不设回合倒计时；仅在解散投票时启动 2 分钟定时器（规则 12.7），超时按同意处理。
- 重连成功后补发视图；客户端不得依赖本地缓存的状态推进对局。

### 11.5 幂等、版本号与并发

- 幂等键：`playerId + reqId`，仅成功操作写入去重表，并落 `game_actions` 唯一索引。
- 状态版本：每次成功操作 `stateVersion + 1`，随响应与推送下发；客户端丢弃小于当前版本的推送。
- 并发：每个房间一个串行执行队列，同房间动作严格按到达顺序执行；不同房间并行。
- 首期单实例部署，因此房间队列用进程内实现即可；多实例前必须补分布式锁或房间亲和路由。

### 11.6 持久化与重启恢复

- `rooms`：房间码、目标人数、房主、状态、创建时间。
- `room_players`：座位、加入顺序、连接状态、准备状态、身份票据摘要。
- `games`：当前 `GameState` 快照、`stateVersion`、`rngState`、胜负。
- `game_actions`：`playerId`、`reqId`、动作类型、`stateVersion`、结果码、时间。
- 每次成功操作在同一事务内写快照与动作记录；服务重启后加载 `playing` 房间，标记所有连接为断开，等待玩家重连。
- 仅靠「种子 + 动作日志」回放不可用，原因是模拟玩家决策消耗随机数（R-05）；恢复必须依赖完整快照。

### 11.7 定时器与解散投票

- 仅解散投票需要定时器：发起后写库、广播、2 分钟到期按同意处理；一票否决立即失败。
- 投票期间暂停对局动作，投票结束后恢复；投票状态是否需要重启恢复见 D-08。
- 首期可用进程内定时器 + 启动时扫描未完成投票，不依赖 Redis。

### 11.8 部署形态建议

- 沿用现有 Ubuntu 24.04 + Nginx：静态站点保持现状，新增 `/api` 与 `/ws` 反向代理。
- Node 进程由 systemd 守护，独立用户运行，日志与配置分离，敏感配置走环境变量或服务器本地文件，不进入仓库。
- 数据库与 Redis（若引入）优先本机或内网，不直接暴露公网。
- 发布前先确认 8.3 与 8.4 的运行时、端口、证书与资源条件。

### 11.9 建议的落地顺序

1. 产品决策：完成第 10 节 D-01 至 D-14 中与首期相关的问题，尤其是 D-01、D-02、D-03、D-04、D-07。
2. 规则引擎工程化：E-01 至 E-08，补齐幂等与版本语义，保持 45 项用例全部通过。
3. 房间内核：`packages/room-core` 实现创建、加入、准备、开始、退出、断线、房主转移、解散投票，并补单测。
4. 服务端最小闭环：单房间、2 名真人、WebSocket 连接、视图下发、动作校验、快照持久化。
5. 恢复与安全：重连、重启恢复、幂等、限流、日志白名单。
6. 多人回归：2 至 5 人真实设备联调，覆盖断线、重复提交、并发、解散投票、淘汰观战（若批准）。
7. 部署与观测：Nginx 配置、systemd、健康检查、日志与告警、部署文档。

### 11.10 明确不在本阶段范围

- 不实现匹配、账号体系、排行榜、好友系统与后台管理端。
- 不实现跨实例部署、Redis 集群与自动扩缩容。
- 不改动卡牌数量、效果、结算顺序与任何已确认规则。
- 不在本任务中创建后端工程或修改现有代码。

## 12. 审计结论

1. 现有工程是一个质量合格的**单机 MVP**：规则引擎与 UI 分离、45 项规则用例全部通过、类型检查通过、CI 覆盖测试与浏览器冒烟、视图裁剪有测试保护。
2. 它不是一个可以「直接加一个 WebSocket」的联机基础：状态与判定都在客户端、身份与会话不存在、房间层只有占位字段、幂等与版本语义不完整、部署过程不可复现。
3. 规则引擎值得复用，且是这次联机改造最大的资产。复用的前提是完成 8 项工程化改造，且不触碰任何规则语义。
4. 房间与身份必须新写，规则 12.5 至 12.8 已经给出足够明确的行为要求，缺的是状态机与传输层。
5. 服务器具备承载后端的基础条件（Ubuntu、Nginx、HTTPS、静态站点已运行），但 Node 运行时、数据库、端口、证书与发布流程均未核实，需在实施前确认。
6. 本阶段建议只确认架构方向与产品决策，不进入编码。下一项任务开始前，需要产品负责人对第 10 节中至少 D-01、D-02、D-03、D-04、D-07 给出结论。
