## 3. 分领域复核

说明：以下问题基于 02 v1.0 的原始设计，保留作为复核证据；第 2.4 节为处理状态，第 4.1 节为 v1.1 修订，第 4.2 节为 v1.2 签收落地，P-19 至 P-21 的落地见 5.6。文中出现的「待 P-xx」「未确认」均为复核时表述，最终状态以第 5 节、第 5.4 节与第 5.6 节为准。

### 3.1 房间与多局对局

#### 3.1.1 现状判断

当前 02 的设计是一房一局：

- `games.room_id uuid NOT NULL UNIQUE`（02 第 7.2 节）。
- ER 图为 `ROOMS ||--|| GAMES`（02 第 7.1 节）。
- 一局结束后 `games.state` 置空，房间进入 `finished`，不再产生第二局。
- T-04 却写明「重开为上一局胜者」，但没有任何字段保存「上一局」与「上一局胜者」，也没有第二局的创建流程。

结论：**当前设计不支持同一房间连续多局**。如果按现状实现，D-01 的「重开时上一局胜者先手」只能理解为新建房间后由玩家手动决定，而新房间没有上一局胜者的可信来源，等于无法实现已确认决策。

#### 3.1.2 一对多改造方案（v1.0 建议，P-15 已批准）

数据库改造：

```sql
-- 现状
-- room_id uuid NOT NULL UNIQUE REFERENCES rooms(id) ON DELETE CASCADE

-- 建议
ALTER TABLE games DROP CONSTRAINT games_room_id_key;
ALTER TABLE games
  ADD COLUMN game_no integer NOT NULL CHECK (game_no >= 1),
  ADD COLUMN start_player_id uuid NULL,
  ADD CONSTRAINT uq_games_room_no UNIQUE (room_id, game_no);
```

说明：

- `game_no` 从 1 开始，同一房间单调递增。
- `UNIQUE (room_id, game_no)` 替代 `UNIQUE (room_id)`。
- `start_player_id` 记录本局起始玩家，便于审计与恢复；第一局为房主，后续为上一局胜者。
- `winner_player_id` 已存在，继续使用。
- 房间表可增加 `current_game_no integer NOT NULL DEFAULT 0`，仅为查询便利，权威仍以 `games` 为准。

状态与流程改造：

| 步骤 | 内容 | 说明 |
| --- | --- | --- |
| 开局 | 计算 `game_no = COALESCE(MAX(game_no), 0) + 1` | 同一房间行锁内计算，避免并发重复 |
| 起始玩家 | `game_no = 1` 取房主；`game_no > 1` 取上一局 `winner_player_id` | 胜者已离开时的回退口径需 P-15 补充 |
| 座位 | 保留原座位与 `joinSequence` | 不因一局结束而重置 |
| 准备状态 | 全部重置为未准备 | 重开前重新准备，符合「全员准备后开始」 |
| 淘汰与观战 | 全部重置为存活、非观战 | 新一局重新开始 |
| 投票 | 清理上一局遗留投票 | 结束时应已无 pending；启动校验兜底 |
| 房间状态 | `playing → finished → waiting` | 需要新增 T-21 转换；`finished` 仍用于展示结算 |
| 持久化 | 每局一行 `games`；已结束局只保留结果与公开事件 | 满足 D-13 |
| 恢复 | 读取 `MAX(game_no)`；若房间为 `waiting` 且上一局已结束，恢复上一局胜者用于下一局 | 不加载已结束局的完整状态 |

风险：

1. 一房多局会让 `games` 行数增长，需要按 D-13 与 P-08 清理。
2. 「胜者已离开」时是否由房主先手，规则与决策均未定义，必须由产品确认。
3. 房间在 `finished` 停留期间是否允许新玩家加入、座位是否保留，需要产品确认。
4. 若产品决定不允许原房间重开，则必须同步修正 D-01 的落地方式：新房间无法继承上一局胜者，除非引入账号体系或跨房间传递凭证；这属于产品口径变更，不得由架构自行决定。

#### 3.1.3 对 02 的最小修订

在 P-15 确认前，02 不应声称已支持重开。v1.1 已将 T-04 的表述改为「新开一局为房主；同房间重开待产品确认」，并在 7.4 增加一房一局的限制说明；P-15 于 2026-11-26 签收后，v1.2 已改为正式支持一房多局，详见 4.2 CH-15、CH-16。

### 3.2 退出、解散投票与断线边界

#### 3.2.1 事件必须分开

| 事件 | 是否改变座位 | 是否改变房主 | 是否发起投票 | 是否暂停对局 | 依据 |
| --- | --- | --- | --- | --- | --- |
| 连接断开 | 否 | 仅开局前房主断线按 12.8 转移 | 否 | 否 | 规则 12.5、12.8 |

### 3.5 数据库与事务

#### 3.5.1 DDL 可执行性静态检查

按 02 第 7.2 节的书写顺序检查：

| 顺序 | 语句 | 依赖 | 结论 |
| --- | --- | --- | --- |
| 1 | 创建 5 个枚举类型 | 无 | 可执行；迁移需防重复创建 |
| 2 | `guests` | 无 | 可执行 |
| 3 | `guest_sessions` | `guests` | 可执行 |
| 4 | `rooms` | 无（房主外键稍后添加） | 可执行；`host_player_id` 先不校验 |
| 5 | `room_players` | `rooms`、`guests` | 可执行 |
| 6 | `ALTER TABLE rooms` 增加房主复合外键 | `room_players` | 可执行；必须 `DEFERRABLE INITIALLY DEFERRED`，建房与建房主需同一事务 |
| 7 | `identity_tickets` | `guests`、`room_players` | 可执行 |
| 8 | `games` | `rooms` | 可执行 |
| 9 | `game_actions` | `games`、`rooms` | 可执行 |
| 10 | `room_dissolution_votes` | `rooms`、`room_players` | 可执行 |
| 11 | `dissolution_vote_ballots` | `room_dissolution_votes` | 可执行，但 v1.0 缺少房间与玩家外键，见 P1-01；02 v1.1 已补 |

补充结论：

- 循环外键（`rooms → room_players → rooms`）依赖延迟约束；插入顺序必须是「房间 → 房主玩家 → 提交」，或先插入房间再在同一事务插入玩家。文档需要写明，否则实现者可能直接插入房间失败。
- `CREATE TYPE` 在同一数据库重复执行会报错，迁移系统必须使用版本表，不得重复执行整段脚本。
- `uq_room_players_one_host`、`uq_room_players_seat_active` 为部分唯一索引，PostgreSQL 支持，语法可执行。
- `games_state_presence` 要求结束对局时在同一事务中把 `state` 置空，否则约束失败。
- `room_dissolution_votes` 的复合外键没有删除策略，物理删除玩家会阻塞，见 P2-01。
- `dissolution_vote_ballots` 的 `player_id` 没有引用 `room_players`，可以写入非本房间玩家，见 P1-01。
- 一房一局限制来自 `games.room_id UNIQUE`，见 P0-01。

#### 3.5.2 建议修正（已写入 02）

- 投票明细表增加 `room_id`，并建立 `(room_id, player_id)` 到 `room_players` 的复合外键；同时建立 `(vote_id, room_id)` 到投票表的复合外键，保证选票与投票属于同一房间。

- 一房多局改造在 v1.0 只在 03 提出；P-15 于 2026-11-26 签收后，v1.2 已写入 02 的 schema、状态机与恢复流程。

- 02 第 8.2 节的事务边界正确：快照、版本、动作日志、房间状态在同一事务。

#### 3.6.2 关键语义问题

1. `room.leave` 与 `vote.start` 重叠：对局中两者都可能触发解散投票，但文档没有说明区别。建议定义 `room.leave` 为「退出意图」，等待房间直接离开，对局中转为发起解散投票；`vote.start` 为「不退出房间、仅申请解散」。
2. `room.sync` 同时承担首次同步与重连，但身份要求不同：前者只需成员会话，后者需要一次性票据。建议在请求中区分 `resume` 模式，或拆为 `room.sync` 与 `room.resume` 两个事件。
3. `game.action` 没有 `baseStateVersion`，服务端无法判断客户端是否基于旧状态提交，`STALE_STATE` 无法产生。建议请求体增加 `baseStateVersion`，服务端在房间队列中比较。
4. `vote.updated` 直接下发逐人票型。规则只要求「全部同意才通过」，未要求公开逐人选择；应默认只下发票数与截止时间，P-16 确认后再决定。
5. `room.leave` 广播给「房间全部成员」包含离开者本人，且离开后不应再订阅房间公开频道。建议离开者只收 ACK，其他成员收 `room.updated`。
6. `room.start` 的 ACK 应返回 `gameId`、`stateVersion`、首局视图版本；否则客户端只能等待推送，易出现空窗。
7. `error` 推送缺少结构，异常断连时客户端无法区分业务错误与传输错误。

### 3.7 断线重启恢复

#### 3.7.1 当前流程的问题

- 02 第 9.1 节先判断截止时间，未先检查拒绝票。由于投票采用一票否决，只要存在拒绝票就应恢复，而不是等到超时按同意处理。
- 02 第 9.1 节对所有未结束房间都「重建房间与引擎」，但 `waiting` 房间与开局前的 `voting` 房间没有 `games` 行，无法重建引擎。
- 02 第 9.2 节「投票期间重启」只写「超时按同意」，未覆盖已存在拒绝票的情况。
- 02 第 8.5 节说明提交失败要回滚内存，但未说明回滚后如何重新加载、何时恢复服务。
- 02 第 9.3 节写「投票期间的断线不改变票权，超时视为同意」，但未说明发起者断线与房主断线的区别。

#### 3.7.2 建议的恢复顺序

1. 检查数据库迁移版本，不匹配则不就绪。
2. 加载 `rooms.status IN ('waiting','playing','voting')` 的房间。
3. 加载 `room_players`，重建座位、`joinSequence`、房主、淘汰与观战状态。
4. 仅对存在对局的房间加载 `games` 最新一行；`waiting` 房间没有对局时跳过引擎重建。
5. 加载 `pending` 投票：先检查是否存在拒绝票；有则按拒绝恢复 `resume_status`；无则按 `deadline_at` 判断超时或注册定时器。
6. 重建每房间串行队列，标记所有连接离线。
7. 注册投票定时器与房间清理任务。
8. 就绪，等待玩家用重连票据恢复。

#### 3.7.3 票据与全员断线

- 票据过期：允许用会话重新申请，座位保留；不得因票据过期淘汰玩家（D-12）。
- 票据重复使用：拒绝并记录；必要时撤销该玩家全部未使用票据。
- 全员断线：进行中的房间保留（D-07），不自动回收；等待房间按 P-07 的 30 分钟阈值清理。
- 进程重启后 `stateVersion` 不重置；客户端以服务端版本为准，不信任本地缓存。
