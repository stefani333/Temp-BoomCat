- 文档版本：v1.0

- 决策阶段：第三阶段——多人联机架构设计前置决策
- 决策人：产品负责人
- 决策依据：《01-现有项目架构审计报告.md》
- 决策状态：D-01 至 D-14 全部已确认

## 1. 总体目标

多人联机采用服务端权威架构。服务端是游戏状态、规则判定、玩家身份和房间生命周期的唯一可信来源。

首期目标是实现好友房间多人对局闭环，支持 Web/PWA 与微信小程序两种客户端形态。

核心原则：

1. 复用现有 `packages/game-core`，不重写卡牌规则。
2. 新增独立房间状态管理能力，不将房间逻辑混入规则引擎。
3. 客户端不得持有完整 `GameState`，只能接收当前玩家对应的 `GameView` 和允许公开的信息。
4. 所有游戏动作必须由服务端验证和执行。
5. 首期采用单服务实例，不引入 Redis 集群或分布式架构。
6. 不擅自修改已经确认的游戏规则。

|---|---|---|
| D-01 | 起始玩家 | 采用 Q-08：第一局默认房主先手；重开时上一局胜者先手；移除手动指定起始玩家入口 |
| D-02 | 客户端形态 | Web/PWA 与微信小程序均纳入目标客户端；具体登录认证方案由架构设计给出建议 |
| D-03 | 数据库 | PostgreSQL |
| D-04 | 实时通信 | Socket.IO |
| D-05 | 后端框架 | MidwayJS |

补充要求：

- D-01 与规则文件第 12.4 节现有文字存在冲突。后续需要制定规则文件同步方案，以 Q-08 为最终产品口径，但本次架构设计不得擅自修改规则文件。
- D-02 的双端支持需要考虑统一协议、身份绑定、重连恢复和客户端差异，不允许为两个客户端分别实现两套游戏规则。
- D-03 使用 PostgreSQL，优先利用事务、唯一约束和 JSONB 能力。
- D-04 使用 Socket.IO，需明确事件协议、ACK、重连、身份认证和消息版本。
- D-05 使用 MidwayJS，遵循仓库 `AGENTS.md` 规范。

## 3. D-06 至 D-10：首期业务范围

| 编号 | 决策主题 | 最终决定 |
|---|---|---|
| D-06 | Redis | 首期不引入 Redis，采用单服务实例 + PostgreSQL 持久化 |
| D-07 | 断线房间回收 | 进行中的房间不因玩家断线自动回收；等待房间和已结束房间分别设计回收策略 |
| D-08 | 解散投票重启 | 投票状态和绝对截止时间持久化；服务重启后继续计时，超时按同意处理 |
| D-09 | 淘汰玩家观战 | 允许观战，但只能看到公开信息，不得看到其他玩家手牌、抽牌堆顺序及其他玩家的私有信息，也不能继续操作 |
| D-10 | AI 补位 | 首期多人联机房间不允许 AI 补位，只允许 2–5 名真实玩家；本地单机模式继续保留 AI |

## 4. D-11 至 D-14：房间与运行规则

| 编号 | 决策主题 | 最终决定 |
|---|---|---|
| D-11 | 房主转移 | 按首次成功加入房间的顺序 `joinSequence` 确定；断线重连不改变顺序；主动退出后重新加入按新顺序计算 |
| D-12 | 超时处理 | 只有解散投票使用 2 分钟倒计时；普通回合和断线均不设置倒计时，不自动出牌、抽牌或淘汰 |
| D-13 | 数据保留 | 进行中的对局保存完整服务端快照；已结束对局仅保留必要结果、公开事件和时间信息；首期不做战绩和排行榜；具体保留期限后续确定 |
| D-14 | 房间号 | 使用 6 位大写字母数字混合码，排除容易混淆的字符；必须有唯一约束和防枚举、限流措施 |

## 5. 首期范围

### 必须实现

- 游客/身份建立机制（具体认证方式待架构设计确定）
- 创建房间、房间码加入
- 2–5 名真实玩家
- 玩家准备、取消准备
- 全员准备后开始游戏
- 服务端唯一执行游戏规则
- 每名玩家收到独立裁剪的游戏视图
- 正常游戏动作与状态同步
- 断线保留座位、身份验证后重连
- 淘汰玩家观战
- 房主转移
- 解散投票与 2 分钟倒计时
- 服务端状态持久化与重启恢复
- 基础安全、限流、日志与健康检查

### 首期明确不做

- 随机匹配
- 好友系统
- 完整账号体系
- 排行榜、战绩系统
- 联机 AI 补位
- 后台管理端
- Redis
- 多实例集群、自动扩缩容
- 任何未经确认的卡牌规则变更

## 6. 架构分层方向

建议采用以下职责分层：

- `packages/game-core`：游戏规则、状态流转、视图裁剪。
- `packages/room-core`：纯 TypeScript 房间状态机。
- `apps/game-server`：MidwayJS 服务端，负责 HTTP、Socket.IO、身份会话、持久化和房间编排。
- `apps/game-web`：Web/PWA 客户端。
- 微信小程序客户端：复用统一服务端协议和规则语义。

分层原则：

- 传输层不写游戏规则。
- 房间层不重复实现游戏规则。
- 规则层不依赖网络、数据库或 UI。
- 完整 `GameState` 只允许在服务端内部流转。
- 客户端不得提交可信的 `playerId` 或 `viewerId`，身份由服务端会话确定。

## 7. 后续待设计而非已定实现细节

以下事项需要架构设计任务提出方案、权衡与推荐，不应擅自当作已经完成：

1. Web/PWA 与微信小程序的认证、游客身份及账号关联策略。
2. Socket.IO 事件协议、ACK、错误码和协议版本。
3. PostgreSQL 表结构、事务边界和索引。
4. 快照与动作日志的一致性方案。
5. 断线重连票据的签发、过期、轮换与撤销。
6. 房间串行队列与并发动作处理。
7. 服务重启后的房间、对局和投票恢复流程。
8. 房间回收的具体时间阈值与清理策略。
9. 已结束对局的数据保留期限。
10. 服务器部署前的环境核查与安全要求。

## 8. 执行约束
