## 1. 目的与判定原则

本文用于确定第二阶段（MVP 收口与工程加固）的开发范围，目标是补齐审计中确认的缺口，不重复开发已经通过验收的能力，也不把官网、后台管理端、多人联网等后续阶段内容提前纳入。

范围判定遵循以下原则：

1. 只有能追溯到审计报告条目、实际代码或现有测试的缺口才纳入。
2. 规则已经通过测试的部分不重做，不因界面调整而改动规则语义。
3. 规则未明确的边界不自行补规则，统一列入第 8 节等待产品确认。
4. 与联网、服务端权威强绑定的能力，不因单机 MVP 的界面需要而提前拆分实现。
5. 新增能力必须服务 MVP 的可用性、数据安全或回归保障，不引入未经确认的业务需求。

### 6.3 可并行与必须串行

- 可并行：S-A1、S-A2、S-B3、S-B4 之间没有代码依赖。
- 可并行：S-B1 与 S-B2 共享状态设计，需要同一位开发者统一字段与序列化版本，避免重复改状态结构。
- 必须串行：S-A2 完成后才能把 S-B1 至 S-B4 的测试纳入稳定门禁。
- 条件串行：S-B5、S-D1、S-D2 必须等待产品确认，未确认前不开发。
- 可延后：S-C1 在阶段 B 后再处理，避免与动作生成顺序调整冲突。

6. 文档同步：范围项完成情况回写到验收测试报告；线框图差异按 Q-06 结果同步。

## 9. 范围外的风险提示

| 风险 | 影响 | 处理 |
| --- | --- | --- |
| 本地快照包含完整对局状态 | 同一设备上的其他使用者可通过开发者工具读取 | 单机 MVP 可接受；服务端阶段改为服务端存储，客户端只持有裁剪视图 |
| 浏览器存储容量与损坏 | 快照写入失败或版本不兼容 | 增加版本号、写入失败提示、损坏快照丢弃并回首页 |
| PWA 与 GitHub Pages 子路径 | 图标与 manifest 路径可能 404 | 使用 Vite `base` 生成路径，构建后校验 `/game/` 下资源 |
| CI 浏览器安装耗时与不稳定 | 发布流水线变慢或偶发失败 | 浏览器测试单独任务，允许重试；单元测试与构建作为必需门禁 |
| 产品确认延迟 | 条件项无法排期 | 阶段 A、B 先交付，条件项单独排期，不阻塞主流程 |
